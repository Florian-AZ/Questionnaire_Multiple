# ADR 000004 — Organisation Git, revue et vérifications

## Statut

Accepté comme convention de travail de l'équipe, mis à jour le 10 septembre 2026.

## Contexte

Le front, le back, le SQL et la documentation doivent évoluer ensemble. Une interface modifiée sans adaptation de l'API ou du guide d'installation rend le projet difficile à utiliser par un autre membre du groupe.

## Décision

Nous conservons une organisation par branches, avec revue avant intégration dans `main`. Les Issues décrivent les tâches et les Pull Requests permettent de présenter les changements avec leur validation.

Cette décision définit le workflow attendu. Elle ne signifie pas qu'une Issue, une Pull Request, un commit ou une intégration a été réalisé pour les modifications actuellement présentes dans le dossier local.

## Workflow prévu

1. Décrire le problème ou la fonctionnalité dans une Issue.
2. Créer une branche dédiée depuis la base de travail de l'équipe.
3. Modifier les composants concernés ensemble : front, contrat API, schémas ou documentation.
4. Vérifier le parcours utilisateur et lancer les tests adaptés.
5. Mettre à jour le README, le runbook et l'ADR concerné si une décision change.
6. Présenter une Pull Request précisant le comportement obtenu, les tests effectués et les limites connues.
7. Faire relire puis intégrer les changements validés dans `main`.

## Fichiers à partager

Le dépôt contient le code, `requirements.txt`, `pyproject.toml`, les scripts SQL, les tests, les guides et `.env.example`.

Les fichiers propres à un ordinateur restent hors du dépôt : `.env`, `.venv`, les bases locales `*.db`, les caches et les réglages d'IDE ignorés par `.gitignore`. Un autre membre installe ses dépendances et configure sa connexion depuis l'exemple fourni.

## Validation attendue

- Démarrer depuis le dossier contenant `main.py`.
- Vérifier que les pages et les fichiers statiques sont accessibles.
- Tester au moins le parcours concerné par la modification.
- Pour une modification métier, exécuter les tests d'intégration du back.
- Pour le front, contrôler la syntaxe JavaScript si Node.js est disponible et vérifier le rendu dans un navigateur.
- Pour une modification SQL, tester l'import et le parcours sur le moteur ciblé ; un test SQLite ne prouve pas à lui seul le fonctionnement MySQL.
- Vérifier que les commandes, adresses et liens de la documentation correspondent à l'application.

La procédure reproductible se trouve dans le [runbook](../runbook/runbook.md). Cette version fournit des tests exécutables localement, sans workflow CI configuré.

## Alternatives considérées

Travailler directement dans `main` réduit le nombre d'étapes mais mélange le développement et la validation. Une documentation séparée des changements de code risque de conserver des instructions obsolètes. Le workflow retenu garde les changements et leur mode d'emploi dans la même revue.

## Conséquences

La revue demande un peu d'organisation, mais permet de vérifier la cohérence entre front, back et mise en place locale. Les résultats de test doivent être rapportés avec leur environnement réel, en distinguant SQLite, MySQL et les vérifications dans le navigateur.
