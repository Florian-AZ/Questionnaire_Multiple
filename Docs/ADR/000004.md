# ADR 000004 — Workflow Git et GitHub

## Statut

Accepté

## Contexte

Nous travaillons en groupe sur une même application de questionnaire. Plusieurs personnes peuvent donc travailler en même temps sur différentes parties du projet.

Pour éviter que les modifications des membres se mélangent directement dans la branche principale, nous devons définir une manière de travailler avec Git et GitHub.

Git et GitHub sont également utilisés dans le cadre du cours.

## Décision

Nous avons choisi de travailler avec **une branche par fonctionnalité ou tâche**.

La branche principale `main` contiendra uniquement les modifications validées.

Lorsqu'un membre termine une tâche, il crée une **Pull Request** vers `main`. Un autre membre du groupe relit alors les modifications avant de valider la Pull Request et de faire le merge.

Les tâches seront suivies avec les **Issues GitHub**.

## Pourquoi ce choix ?

Ce fonctionnement permet à chaque membre de travailler sur sa partie sans modifier directement la branche principale.

La Pull Request permet également de faire relire le travail par un autre membre avant de l'intégrer.

Nous avons choisi ce fonctionnement car il correspond à ce que nous avons vu en cours et qu'il est adapté à notre travail en groupe.

## Workflow

Pour chaque tâche :

1. Une Issue est créée et attribuée à un membre.
2. Le membre crée une branche pour cette tâche.
3. Il réalise les modifications et fait ses commits.
4. Il ouvre une Pull Request vers `main`.
5. Un autre membre effectue une code review.
6. Après validation, la Pull Request est mergée dans `main`.
7. L'Issue est ensuite fermée.

## Alternatives envisagées

Nous aurions pu travailler directement sur `main`.

Cependant, cette méthode présente plus de risques de conflits et ne permet pas de faire une véritable étape de relecture avant l'intégration des modifications.

Nous avons donc choisi de séparer le travail avec des branches et des Pull Requests.

## Conséquences

### Conséquences positives

- Chaque membre peut travailler indépendamment sur sa tâche.
- La branche `main` reste plus propre.
- Les modifications sont relues avant leur intégration.
- Les tâches et leur avancement sont visibles grâce aux Issues.
- L'historique du projet permet de suivre le travail réalisé par chaque membre.

### Conséquences négatives

- Le workflow demande un peu plus d'organisation.
- Des conflits peuvent tout de même apparaître lors des merges.
- Chaque membre doit respecter les règles définies par le groupe.

## Conclusion

Nous avons choisi ce workflow afin d'organiser le travail entre les membres du groupe et de limiter les problèmes liés aux modifications simultanées.

L'utilisation des branches, des Pull Requests, des code reviews et des Issues permet de garder un projet organisé tout au long du développement.
