# ADR 000005 — Serveur unique et accès local au site

## Statut

Accepté et mis en place le 10 septembre 2026.

## Contexte

Le front et le back étaient séparés. Ouvrir un fichier HTML ne démarrait pas l'API, et les commandes de lancement pouvaient pointer vers une application ne servant pas l'interface. Le projet doit pouvoir être ouvert dans VS Code et testé sans configurer deux serveurs.

## Décision

Un seul processus **Uvicorn** exécute `main:app`. FastAPI sert :

- les vues du site aux adresses `/`, `/catalogue`, `/creer` et `/jouer` ;
- les ressources du frontend sous `/static` ;
- les données et opérations métier sous `/api` ;
- la documentation interactive sous `/docs`.

Le navigateur utilise la même origine pour le front et l'API. Aucun serveur Live Server ni réglage CORS pour un frontend séparé n'est nécessaire dans cette configuration.

Le lancement fourni écoute sur **127.0.0.1:8000**. Depuis VS Code, l'utilisateur peut choisir un autre port avec `--port`, par exemple 8001, sans modifier le JavaScript.

Sous Windows, `Demarrer.bat` prépare les dépendances si nécessaire et appelle `lancer.py`, qui démarre le serveur et tente d'ouvrir le navigateur lorsque la page d'accueil répond. Le lanceur utilise le port 8000 et n'active pas le rechargement automatique. La commande Uvicorn du runbook permet d'ajouter `--reload` pour le développement.

## Accès et connexion

L'utilisateur ouvre l'adresse HTTP du serveur dans son navigateur. Il n'y a pas de compte, de mot de passe ni de session d'authentification dans cette version ; le pseudo sert à identifier l'auteur ou la participation.

La connexion à la base de données est distincte de l'accès au site. Elle est établie par le back à partir de `DATABASE_URL`, selon [l'ADR 000002](000002.md). Les identifiants MySQL ne sont pas saisis dans une page de connexion du site.

La liaison à `127.0.0.1` limite l'écoute à l'ordinateur local. Le projet ne contient pas de configuration d'hébergement public ou d'accès depuis d'autres appareils.

## Alternatives considérées

- **Ouvrir directement les fichiers HTML** : ne fournit pas le serveur nécessaire aux opérations métier.
- **Deux serveurs, front et API** : augmente les ports et paramètres à synchroniser sans bénéfice pour le périmètre actuel.
- **Déploiement public immédiat** : hors du périmètre de la mise en place locale ; nécessiterait une configuration et des décisions supplémentaires.

## Conséquences

Une seule commande rend le site et l'API disponibles. Le serveur doit rester actif pendant l'utilisation. Un changement de port implique d'ouvrir la nouvelle adresse ; le stockage navigateur du brouillon dépend aussi de cette adresse.

L'interface statique peut encore être servie en cas d'erreur de requête MySQL. Les opérations dépendantes de la base affichent alors l'erreur renvoyée par l'API. Une page d'accueil HTTP disponible ne suffit donc pas à prouver que la base est opérationnelle.
